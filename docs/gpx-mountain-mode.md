# Горный режим: GPX, профиль высот и план по GAP

Статус: решения по основным вопросам согласованы, реализация не начата.
Открытых вопросов по дизайну нет; мелкие детали выбраны по умолчанию и
перечислены в тексте.

Документ фиксирует решения по фиче «горный режим»: импорт GPX, чекпойнты,
ряд подъём/спуск, карта высот, стоянки и пересчёт плана по Minetti GAP.

---

## 1. Принятые решения

- Горный режим включается отдельным чекбоксом в меню-шестерёнке. В обычном
  режиме поведение таблицы не меняется.
- GPX хранится целиком файлом в каталоге приложения. В `SharedPreferences`
  лежат только метаданные и путь.
- Высоты берутся из трека **как есть, без сглаживания и без порога**.
  D+/D− считаются по сырым `ele`. Сглаживание применяется только к цвету
  графика (окно 100 м), иначе профиль рябит.
- Расчёт поправки темпа — Minetti GAP, интегрирование по треку, 3D-дистанция.
- Чекпойнты из трека — только `wpt` и границы `trkseg`. Произвольную
  расстановку не делаем.
- При импорте два режима: «только финиш» и «финиш + чекпойнты».
- Отрезанные при нормализации части имени не выбрасываются, а дописываются
  в заметку ряда ПП.
- Пользователь вводит итоговое время **с учётом стоянок**.
- Стоянки привязаны к чекпойнтам, редактируются свободно и не меняют
  ходовые темпы сегментов.
- Правки пользователя — актуальное состояние. Историю и «оригинал» не храним.
- В имперской системе ряд высот показывается только в футах.
- Экспорт TCX пока неактивный пункт меню; модель данных должна его допускать.

## 2. Модель данных

### 2.1. Расширение `PaceTableData`

Добавляются поля:

```dart
final bool mountainMode;
final List<int> planStops;          // секунды, по колонкам-ПП
final PlanAnchor? planAnchor;       // опора пересчёта
final TrackSlots tracks;            // основной/резервный трек и активный
final TrackSummary? trackSummary;   // кэш сегментных данных на случай потери файла
final List<int?> manualAscent;      // ручные D+, метры; null — брать из трека
final List<int?> manualDescent;     // ручные D−, метры; null — брать из трека
```

`PlanAnchor`:

```dart
enum PlanAnchorKind { flat, targetTime, targetPace, manual }

class PlanAnchor {
  final PlanAnchorKind kind;
  final double? flatPaceSecPerKm;   // для flat
  final int? targetTotalSec;        // для targetTime, вместе со стоянками
  final double? targetMovingPaceSecPerKm; // для targetPace
}
```

`TrackSlots`:

```dart
class TrackSlots {
  final String active;              // 'primary' | 'backup'
  final TrackMeta? primary;
  final TrackMeta? backup;
}

class TrackMeta {
  final String relativePath;        // tracks/<key>/primary.gpx
  final String originalName;
  final int importedAtMs;
  final int points;
  final double lengthM;
  final double ascentM;
  final double descentM;
  final bool hasElevation;
  final double offsetM;             // сдвиг начала трека относительно старта
}
```

`TrackSummary`:

```dart
class TrackSummary {
  final String source;              // primary/backup/manual
  final List<SegmentStats> segments;
  final List<double> profile;       // [km, ele, km, ele, ...], ~500–1000 точек
}

class SegmentStats {
  final double ascentM;
  final double descentM;
  final double gapFactor;           // множитель к плоскому темпу
  final double lengthM;             // 2D-длина сегмента
}
```

`gapFactor` не зависит от опорного темпа: это отношение ходового времени
сегмента к времени по плоскому темпу. Это позволяет пересчитывать план при
смене темпа без повторного прохода по треку.

Старые таблицы загружаются с `mountainMode: false`, пустыми стоянками,
`tracks: null`, `planAnchor: null`. Схема хранилища поднимается на версию.

### 2.3. Хранение треков

- Каталог: `getApplicationSupportDirectory()/tracks/<distanceKey>/`.
- Файлы: `primary.gpx`, `backup.gpx`.
- `distanceKey` — стабильный FNV-1a хеш от `eventName + "\u0000" + distanceName`,
  16 hex-символов. `String.hashCode` не используем: он не гарантирован между
  версиями Dart.
- В JSON хранится **относительный** путь: на iOS абсолютный путь контейнера
  меняется между запусками.
- Запись атомарная: `<file>.tmp` → `rename`.
- При удалении дистанции удаляется весь каталог.
- При повторном импорте в занятый слот — подтверждение перезаписи. Второй слот
  не трогаем.
- Если файл пропал: `available = false`, план и график работают по
  `trackSummary`; в меню показывается «трек недоступен, импортируйте заново».
- Полный трек в `SharedPreferences` не кладём: XML на 0.1–2 МБ читался бы при
  каждом старте.

## 3. GPX: парсинг и подготовка

### 3.1. Что читаем

- `trk/trkseg/trkpt`: `lat`, `lon`, `ele`, `time`.
- `wpt`: `lat`, `lon`, `name`.
- `rte/rtept` — опционально, как дополнительные кандидаты (не в MVP).
- `time` в расчётах не участвует: в предоставленных треках он фиктивный
  (`1970-01-01T00:00:01`). Нужен только для будущего экспорта.
- Несколько `trk`: предлагаем выбрать трек; по умолчанию первый с точками.
- Несколько `trkseg`: склеиваем в один маршрут. Если разрыв между последней
  точкой сегмента и первой точкой следующего больше 200 м, предупреждаем:
  возможно, это не пауза, а разные участки.
- Нет `ele`: `hasElevation = false`; горный режим работает только с ручными
  высотами, график показывает «нет данных о высоте».
- Битые/дублирующиеся точки: пропускаем точки с 2D-шагом < 0.5 м.
- Ограничение размера: до 200 000 точек и до 50 МБ; больше — отказ с
  сообщением.

### 3.2. Расстояния

- `ds2d` — haversine по координатам.
- `ds3d = sqrt(ds2d² + dele²)` — для интегрирования времени по Minetti.
- Накопленное расстояние для таблицы и финиша — **2D**: километры трассы,
  которые видит пользователь.
- Санитарная защита от выбросов: если `|dele| / ds2d > 1.0` (круче 100%),
  для `ds3d` ограничиваем `dele` значением `ds2d`. На сырых высотах это
  защищает от одиночных spikes.
- `offsetM` — сдвиг начала трека. Если трек начинается не со старта
  (подводка), после сопоставления предлагаем сдвинуть все километры на
  `offsetM`, чтобы старт соответствовал 0.

### 3.3. Высоты

- D+/D− и профиль — по сырым `ele`.
- Порог и сглаживание **не применяются**.
- Следствие: на треках из DEM значения уже гладкие, на барометрических
  треках D+ будет завышен. Пользователь может править D+/D− вручную.
- Для цвета графика крутизна считается по окну 100 м (визуальное сглаживание).
  Это не меняет D+/D− в таблице.

## 4. Импорт

### 4.1. Точки входа

Меню-шестерёнка (заменяет кнопку `+− ПП`):

- `+− ПП` — существующий диалог количества колонок.
- `Горный режим` — чекбокс.
- `Загрузить трек GPX` — выбор файла и слота (основной/резервный).
- `Основной / резервный трек` — переключатель активного слота, если треки есть.
- `Править высоты вручную` — доступно и без трека.
- `Выгрузить план TCX` — неактивный пункт с подсказкой «скоро».

Если таблица заблокирована, перед импортом/правкой спрашиваем
«Разблокировать?».

### 4.2. Два режима импорта

1. **Только финиш.** Ничего не делаем с промежуточными ПП. Записываем
   `distances.last = trackLength2D`. Показываем дельту. Если финиш оказывается
   раньше последнего ПП — предупреждение и отказ.
2. **Финиш + чекпойнты.** Открываем сравнительную таблицу (см. 4.5).
   В сравнительной таблице каждая колонка получает флажок «актуализировать из
   трека». По умолчанию отмечены колонки с однозначным совпадением, остальные
   пользователь выбирает сам. Неотмеченные колонки не меняются.

Если таблица пустая и кандидатов нет, доступен только первый режим.
Если кандидаты есть — второй режим доступен и на пустой таблице.

### 4.3. Кандидаты

- `wpt` с именем — всегда.
- Границы `trkseg` — если сегментов больше одного; имена «Сегмент 2», «Сегмент 3».
- Кандидат считается лежащим на треке, если минимальное расстояние до
  любой точки ≤ 250 м. Автоподсказка — только если ≤ 100 м.
- Показываем все проходки точки: одно имя может встречаться на треке
  несколько раз.

Примеры из реальных треков:

| Файл | `wpt` | Особенность |
|---|---:|---|
| GRUT T100 | 19 | `CP2/5` → 18.76 и 94.00 км; `Start/Finish` → 0 и 109.31; есть `Брод`, `MP`, `ToD`, `Понтон` |
| MFU K40 | 4 | `СР2` — кириллица; `CP1` имеет две проходки: 14.87 и 15.66 км |
| VR100 | 10 | `CP8` — 139.69 и 140.49 км; порядок `wpt` не совпадает с порядком трассы |
| WBU L120 | 8 | порядок полностью перемешан; `CP3-Вода`, `CP7-Вода` |

`ToD end` в GRUT лежит в 165 м от трека — это кандидат «вне трека»,
не ПП.

### 4.4. Нормализация имени и заметки

1. Убираем лишние пробелы, приводим к верхнему регистру для сравнения.
2. `СР` → `CP` (кириллица), `КП` → `CP`.
3. `START/FINISH` и `СТАРТ/ФИНИШ` разбираем как два ярлыка: `START`, `FINISH`.
4. `CP2/5` разбираем как `CP2` и `CP5`.
5. Отрезаем суффиксы: `(...)`, `-Вода`, `-Water`, хвостовое `Вода`.
   Отрезанный текст **не выбрасываем**, а дописываем в заметку колонки:
   - пустая заметка → суффикс;
   - непустая → `старая заметка · суффикс`;
   - если суффикс уже есть → не дублируем.
6. Базовое имя (`CP3`, `СР9`, `Start`, `Finish`) в заметку не пишем:
   заметка — это пользовательская подпись, ломать её нельзя.
7. `CPn` / `СРn` даёт номер колонки `n` (1-based, без старта и финиша).
   `Start` → колонка 0, `Finish` → последняя. Если номер вне диапазона —
   только сопоставление по расстоянию.
8. `MP`, `PP`, `ToD`, `Брод`, `Понтон` — кандидаты, но не авто-ПП.

### 4.5. Сопоставление

Сравнительная таблица:

```
Колонка | Лимит | Сейчас, км | Кандидат        | По треку, км | Δ      | На треке
1 CP1   | 07:00 | 11.0       | CP1 (проходка 1)| 10.84        | −0.16  | 5 м
2 CP2   | 08:00 | 18.8       | CP2/5 (проходка 1)| 18.76      | −0.04  | 6 м
...
```

Алгоритм:

1. Для каждого кандидата считаем все проходки: локальные минимумы расстояния
   до трека < 250 м, слипающиеся в пределах 500 м.
2. Сортируем кандидатов по километру.
3. Для каждой колонки:
   - если есть однозначное совпадение по нормированному имени и номеру —
     предлагаем его;
   - иначе берём проходку, ближайшую к текущему расстоянию колонки;
   - допуск автоподсказки: `min(0.5 км, 5% длины трека)`;
   - если расстояний в таблице нет, используем только именованное
     сопоставление; произвольно не расставляем.
4. Одна проходка не может быть назначена двум колонкам. Если имя
   многозначное (`CP2/5`), разным колонкам назначаются разные проходки по
   порядку.
5. Если проходок у имени больше, чем колонок, лишние показываем, но не
   применяем.
6. Конфликты и выход за допуск подсвечиваем; пользователь правит вручную.

Применение:

- обновляем `distances` только у отмеченных колонок;
- заметки дополняем суффиксами (см. 4.4);
- лимиты, вода, еда, плановые значения не трогаем;
- финиш всегда можно привязать к концу трека;
- после применения пересчитываем высоты и план (см. 7).

### 4.6. Старт трека

Если расстояние от первой точки трека до точки `Start` больше 200 м,
спрашиваем пользователя, что считать стартом:

- **а)** точку трека, ближайшую к `Start` (километры отсчитываются от неё);
- **б)** начало трека как есть.

Без подтверждения сдвиг не применяем. Выбранный вариант хранится в `offsetM`.

## 5. Высоты

### 5.1. Сегментные D+/D−

- Границы сегментов — расстояния колонок.
- Трек ресемплируется в границах: интервалы точек, пересекающие границу,
  делятся пропорционально.
- D+ = сумма положительных приращений сырых `ele` внутри сегмента,
  D− = сумма модулей отрицательных.
- Если колонка выходит за трек — сегмент помечается «нет данных», фактор 1.
- Немонотонные расстояния — ошибка валидации, пересчёт не выполняется.

### 5.2. Ручные высоты

- Правим только D+ и D− по сегментам.
- Значение `null` — берём из трека; число — переопределяем.
- Если трека нет, все сегменты должны иметь ручные значения (иначе 0/0).
- Синтетический профиль сегмента для GAP:
  - длина `L`, подъём `A`, спуск `D`;
  - `L_up = L * A / (A + D)`, `L_down = L - L_up` (при `A + D > 0`);
  - сначала линейный подъём на `A` на `L_up`, затем линейный спуск на `D`
    на `L_down`;
  - если `A = 0` или `D = 0` — один линейный участок;
  - абсолютная высота начала не важна, важны только уклоны.
- Никаких пометок «приблизительно» не ставим: пользователь понимает, что
  ввёл сам.
- Если трек есть и ручные значения заданы, для сегмента используется
  синтетический профиль, а не трек. Для остальных — трек.

### 5.3. Формат ряда

- Метрика:
  - каждое число < 100 м → целые метры: `90`;
  - ≥ 100 м → десятые километра: `1.2`;
  - разделитель `-`, например `90-11`, `1.2-0.3`;
  - если помещаются стрелки: `↑1.2 ↓0.3`.
- Имперская система: **только футы**, целые: `295-36`, со стрелками
  `↑295 ↓36`. Километры в этом ряду не показываем.
- Первая клетка ряда — служебная: `↑↓` (или `НАБОР` при достаточной ширине).
- Итог: сумма D+ и D− по сегментам. В портрете — отдельный ряд под рядом
  высот; в ландшафте — колонка `Total`.
- Отрицательных значений быть не может; `0` показываем как `0`.

## 6. GAP / Minetti

### 6.1. Формула

Энергозатраты (Minetti et al., 2002):

```
Cr(i) = 155.4·i⁵ − 30.4·i⁴ − 43.3·i³ + 46.3·i² + 19.5·i + 3.6
```

`i` — уклон (`Δh / Δs2d`), `Cr` — Дж/(кг·м).

Коэффициент к плоскому темпу:

```
k(i) = Cr(i) / Cr(0),   Cr(0) = 3.6
```

Важно: именно `Cr(i) / Cr(0)`, а не наоборот. При подъёме `k > 1`
(медленнее), при спуске `k < 1` (быстрее).

Примеры:

| Уклон | k (Minetti) | k (в расчёте) | Темп при плоском 6:00/км |
|---|---:|---:|---:|
| 0% | 1.00 | 1.00 | 6:00 |
| +5% | 1.30 | 1.30 | 7:49 |
| +10% | 1.66 | 1.66 | 9:57 |
| −5% | 0.76 | 0.76 | 4:34 |
| −10% | 0.60 | 0.70 | 4:12 |

### 6.2. Ограничения

- Уклон обрезаем до `[−0.25, +0.25]`: за пределами полином экстраполируется.
- Спуск: `k = max(k, 0.70)`, то есть не быстрее чем на 30% от плоского.
  Без этого Minetti даёт нереалистичные 3:35/км на −10%.
- Константы `MIN_GRADE`, `MAX_GRADE`, `MIN_K` выносим в одно место и
  покрываем тестами.

### 6.3. Интегрирование

Идём по точкам трека:

```
moving = 0
for each interval (p_i, p_{i+1}):
  ds2 = haversine
  if ds2 < 0.5 m: continue
  dh = ele[i+1] - ele[i]
  grade = clamp(dh / ds2, MIN_GRADE, MAX_GRADE)
  k = max(Cr(grade) / Cr(0), MIN_K)
  ds3 = sqrt(ds2² + dh²)
  moving += ds3 * flatPacePerMeter * k
```

`flatPacePerMeter = flatPaceSecPerKm / 1000`.

Границы сегментов делят интервал пропорционально; высота на границе
интерполируется линейно.

Для сегмента храним:

```
gapFactor = moving / (length2D * flatPacePerMeter)
```

Если высот нет: `gapFactor = 1`, `moving = length2D * flatPacePerMeter`.

Шум в сырых высотах слегка завышает GAP из-за нелинейности `Cr` (неравенство
Йенсена). Это принятое следствие решения «сырые данные»; на DEM-треках эффект
мал.

## 7. План

### 7.1. Величины

- `moving_i` — ходовое время сегмента, без стоянок.
- `stop_i` — стоянка на ПП `i`, секунды.
- `arrival_i = start + Σ_{j≤i} moving_j + Σ_{j<i} stop_j`.
- `departure_i = arrival_i + stop_i`.
- `movingTotal = Σ moving_i`.
- `totalTime = movingTotal + Σ stop_i`.
- `summaryPace = movingTotal / totalDistance` — ходовой средний темп.
- Итоговое время включает стоянки; итоговый темп — ходовой.

Это согласуется с «стоянка увеличивает итоговое время»: стоянка не меняет
ходовые темпы, но сдвигает последующие прибытия и увеличивает итог.

### 7.2. Опора плана (`planAnchor`)

- `flat(p0)` — все сегменты считаются от плоского темпа `p0` и GAP-факторов.
- `targetTime(T)` — ходовое время нормируется так, чтобы
  `movingTotal + stops = T`.
- `targetPace(p)` — ходовое время нормируется так, чтобы
  `movingTotal / D = p`.
- `manual` — источник истины текущие сегментные темпы; глобальной нормировки
  нет. Правка времени или темпа сегмента — это дельта: новое время минус
  старое прибавляется ко всем последующим плановым временам до последней
  заполненной колонки (как в `_finalizePlanEdit`). Темпы последующих
  сегментов не меняются, потому что их длительности те же.

Переходы:

| Действие | Новый якорь |
|---|---|
| Ввод итогового темпа «плоский» | `flat(p0)` |
| Ввод итогового времени «плоский» | `flat((T − stops) / D)` |
| Ввод итогового темпа «с поправкой» | `targetPace(p)` |
| Ввод итогового времени «с поправкой» | `targetTime(T)` |
| Ручная правка темпа/времени сегмента | `manual`; дельта к последующим прибытиям |
| Правка стоянки | якорь сохраняется; дельта `Δстоянки` к последующим прибытиям |
| Правка расстояния ПП/финиша | якорь сохраняется и применяется заново |
| Смена/импорт трека, правка высот | якорь сохраняется и применяется заново |
| Включение горного режима | пересчёт по текущему якорю |
| Выключение горного режима | план не перезаписываем, только скрываем ряд и график |

### 7.3. Диалог «плоские или с поправкой»

Показывается при вводе итогового темпа/времени, если горный режим включён и
есть высоты. Содержит:

- переключатель «Плоские данные / Уже с поправкой на высоты»;
- поле «Стоянки, мин» (по умолчанию 0);
- предпросмотр (только в диалоге, в таблицу не попадает): «Плоский 6:00 → расчётный 6:38, итог 12:34 (со стоянками 45 мин)».

Математика:

- «Плоские»: `p0 = введённый темп` (или `(время − стоянки) / D`);
  `moving_i = length_i * p0 * gapFactor_i`; итог = moving + стоянки.
- «С поправкой»: сначала считаем `moving_i` по GAP, затем
  `λ = targetMoving / Σ moving_i`; умножаем все `moving_i` на `λ`.
  Для времени `targetMoving = T − Σ stops`; для темпа
  `targetMoving = p * D`.

Плоское значение в таблице не показываем: клетка показывает фактический
темп сегмента (с учётом GAP). Плоская опора хранится в `planAnchor` для пересчёта.

### 7.4. Стоянки

- Ряд стоянок появляется по долгому нажатию на первую клетку ряда
  `Плановый темп`.
- Первая клетка делится по диагонали: сверху справа `pace`, снизу слева
  `↓ t stops`. При раскрытии стрелка поворачивается.
- Редактирование: целые минуты (внутренне — секунды), пусто = 0.
- Стоянка привязана к ПП и сдвигает только последующие прибытия.
- Красная подсветка `План`: если `arrival_i + stop_i > limit_i`.
  Семантическая подсказка: «стоянка выводит за лимит».
- Итоговые стоянки: колонка `Total` в ландшафте. В портрете отдельной
  итоговой строки нет; есть только редактируемый ряд по ПП.
- Если раскрытый ряд стоянок не помещается в ландшафте, таблица получает
  вертикальную прокрутку только в этом состоянии; в свёрнутом виде все ряды
  по-прежнему помещаются.
- Глобальный переключатель в меню-шестерёнке «Темп сегмента: чистый /
  с учётом стоянок», по умолчанию «чистый». Каждый сегмент отдельно не
  настраивается.
  - «чистый» — клетка показывает ходовой темп сегмента;
  - «с учётом стоянок» — `(arrival_i − arrival_{i−1}) / distance_i`, то есть
    со стоянкой на предыдущем ПП.
  Внутри всегда хранится чистый темп.

Про поле «Стоянки, мин» в диалоге: это **суммарное** время. Если ряд по ПП
пуст, сумма распределяется равномерно по промежуточным ПП (остаток — в
последний). Если ряд заполнен, поле показывает текущую сумму; изменение
суммы масштабирует значения пропорционально. Если нужна другая логика —
это одна функция, меняется без переделки модели.

### 7.5. Пересчёт

Все правила работают на текущем состоянии. Историю и «оригинал» не храним.

| Триггер | Что пересчитываем |
|---|---|
| Правка темпа/времени сегмента `i` | дельта к прибытиям `i+1…`; итоги; якорь → `manual` |
| Правка стоянки `i` | дельта `Δстоянки` к прибытиям `i+1…`; итоги; красные статусы; темпы не меняются |
| Правка расстояния ПП `i` | сегменты `i−1` и `i`: `p_flat = pace / gap`, затем `pace' = p_flat * gap'`; прибытия; при целевом якоре — нормировка λ |
| Правка финишного расстояния | последний сегмент по `p_flat * gap'`; при целевом якоре — нормировка λ по всем сегментам; затем прибытия и итоги |
| Добавление/удаление колонки | структура; новые сегменты с `gapFactor = 1`; при целевом якоре — нормировка |
| Импорт/смена трека | все `gapFactor`; затем по якорю |
| Правка ручных D+/D− | `gapFactor` затронутых сегментов; затем по якорю |
| «Если сомневаемся» | полный пересчёт от текущего якоря: `flat` → GAP; `targetTime/targetPace` → GAP + λ; `manual` → `p_flat_i * gap_i` |

`p_flat_i = pace_i / gapFactor_i` — «плоский эквивалент» сегмента. Он
сохраняет намерение пользователя при изменении границ.

Ручная правка сегмента переводит якорь в `manual`: правка пользователя важнее
ранее введённого итога. Если пользователь снова вводит итог — якорь снова
становится целевым.

История правок и «оригинал» не хранятся: пересчитывается только то, на что
повлияла последняя правка.

## 9. Производительность

- Парсинг, расчёт расстояний, D+/D− и кандидатов — в `Isolate` (`compute`).
  Наружу возвращаем компактный результат: типизированные массивы и
  даунсемплированный профиль.
- 100k точек: парсинг в фоне, UI не блокируется.
- График: min/max по пиксельным бакетам, кэш `Path`, перерисовка только на
  жест/смену окна.
- GAP: считаем один раз на трек/границы, храним `gapFactor` по сегментам.
  При правке темпа повторно по точкам не идём.
- Профиль для графика: 2–4 уровня детализации или пересчёт по окну.
- GPX не кладём в `SharedPreferences`.
- Кэш трека в памяти — на открытую дистанцию; при переключении дистанции
  можно выгружать.

### 11.1. Далёкое будущее (вне текущего плана)

Обсуждено и отложено. Не реализуем в текущем плане; при возврате начинать с этого описания, заново не обсуждать.

**Карта высот как ряд таблицы (вместо диалога).**
- Вид карты — раскрывающийся ряд таблицы, как ряд стоянок (`_stopsRowOpen`): внутри таблицы, в обеих ориентациях.
- Первый этап: только вид, без активных элементов — профиль высот (`CustomPaint`) на всю ширину таблицы, ПП отмечены вертикальными линиями на своих км. Ось X — дистанция трека. В ландшафте профиль сжат по ширине, но читаем.
- Текущая карта (`_openElevationChart`, диалог) остаётся до второго этапа. Рисовальщик выносится в отдельный виджет, который используется и в диалоге, и в ряду — второй этап (подсказки, расширения) добавляется без переделки.
- Вариант «колонки» (каждая колонка — сегмент ПП) отвергнут: не отражает рельеф между ПП.

**Учёт стоянок в темпе сегмента (чекбокс «Темп сегмента: с учётом стоянок»).**
- Проблема: при стоянке на ПП 5 отбытие смещается (10:00 → 10:05), и при сохранении темпа 6:00 прибытие на ПП 6 сдвигается (11:00 → 11:05). Есть два способа учесть стоянку:
  - **A (реализован):** темп сегмента не меняется, прибытия сдвигаются на стоянку.
  - **B (отложен):** время прибытия не меняется, а темп сегмента ускоряется, чтобы уложиться в плановое время с учётом стоянки: `(прибытие_i − прибытие_{i−1} − стоянка_{i−1}) / расстояние_i`.
- В текущем плане выбран A. Вариант B — отдельная фича, для неё нужен чекбокс в меню (сейчас пункт отображается серым с пометкой «отложено»).
- Производная `(прибытие_i − прибытие_{i−1}) / расстояние_i` из §7.4 — это средний темп со стоянкой (медленнее ходового), а не вариант B. Решение по ТЗ пересмотреть при возврате к фиче.
