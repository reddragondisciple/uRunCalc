# Погода, покрытие и кроссовки: автоматическая поправка темпа

Статус: дизайн согласован, реализация не начата.
Дата: 2026-11-10.
Основа — обсуждение в сессии; смежные решения по горному режиму —
`docs/gpx-mountain-mode.md`.

Документ фиксирует, как uRunCalc автоматически учитывает покрытие трассы,
погоду и кроссовки при расчёте плана. Ручной ввод — только как дополнение
позже; по умолчанию всё берётся из API по координатам трека.

---

## 1. Что решаем

Сейчас план считается по GAP (Minetti) и плоскому темпу. Фактический темп
зависит ещё от трёх групп факторов:

- **покрытие** — асфальт, грунт, трава, песок, грязь, снег, броды;
- **погода** — жара и влажность, дождь, снег, ветер (ветер отложен);
- **кроссовки** — дорожные, трейловые, минималистичные.

Цель — не «угадать» темп, а дать прозрачную поправку с настраиваемыми
коэффициентами и возможностью откалибровать их на реальных треках.

База: **сухой асфальт, дорожные кроссовки = 1.00**. Все остальные факторы
умножаются на неё.

---

## 2. Принятые решения (кратко)

- Покрытие и погода **не занимают отдельную строку таблицы**. Они рисуются
  на графике высот (см. §11).
- Включаются чекбоксами в меню-шестерёнке: `Покрытие`, `Погода`,
  `Кроссовки`. Чекбокс открывает диалог и остаётся снятым, пока диалог не
  подтверждён.
- Данные — автоматически из API по координатам трека и времени старта.
- Погода: **Open-Meteo** основной провайдер; MET Norway (yr.no) — запасной
  для прогноза. Интерфейс `WeatherProvider` — под будущий прокси/кэш.
- Если прогноза нет (только климатические нормы) — **погодная полоса не
  показывается вообще**, а погодный множитель = 1.00.
- Покрытие: **OpenStreetMap** через Overpass API. Для уточнения
  неизвестного покрытия берём **все доступные источники**: OSM
  (`natural`, `landuse`, `wetland`, `seasonal`, `tracktype`), ESA WorldCover,
  Copernicus Land Cover, MODIS, SoilGrids.
- Снег зависит не только от глубины, но и от температуры (плотность) и
  населённого пункта: в городе часть снега расчищена, возможны асфальт,
  укатанный снег или лёд; в сёлах чистят меньше, за городом снег полный.
- Укатанность трассы — **переключатель** в диалоге погоды, по умолчанию
  **выключен**. Включённый означает, что снег укатан организаторами или
  бегунами: эффективная глубина уменьшается, состояние сдвигается к
  `packed`; даже когда условия не дают снегу слежаться, впереди идущие
  всё равно снижают глубину от максимума.
- Неизвестное покрытие = **грунт** (`dirt`), с показом процента покрытия.
- Один **глобальный** профиль коэффициентов (не на дистанцию).
- Приложение бесплатное, некоммерческое — лимиты Open-Meteo подходят.
- Треки могут быть **неполными (DNF)** — это не ошибка, считаем только
  пройденную часть.
- Калибровка — на реальных треках с исторической погодой; время в треке
  обязательно.

## 3. Формат трека: GPX предпочтителен

В `userTracks/` лежат три реальных трека в трёх форматах. Замеры:

| Файл | Формат | Размер | Точек | Время | Высота |
|---|---|---:|---:|---|---|
| `20250614Outdoor run` | GPX 1.0 | 1.68 МБ | 14 477 | есть, UTC | есть |
| `20250614Outdoor run` | TCX | 3.29 МБ | 14 477 | есть | есть |
| `20250614Outdoor run` | KML | 3.53 МБ | 14 479 Placemark | в `TimeSpan` | есть |
| `20250727Outdoor run` | GPX 1.0 | 3.04 МБ | 26 160 | есть, UTC | есть |
| `20250727Outdoor run` | TCX | 5.95 МБ | 26 160 | есть | есть |
| `20250727Outdoor run` | KML | 6.39 МБ | 26 162 Placemark | в `TimeSpan` | есть |
| `20251221Outdoor run` | GPX 1.0 | 2.93 МБ | 25 127 | есть, UTC | есть |
| `20251221Outdoor run` | TCX | 5.71 МБ | 25 127 | есть | есть |

Вывод: **GPX — предпочтительный формат**.

- он самый компактный (почти в 2 раза меньше TCX и KML);
- уже поддерживается `parseGpx` (GPX 1.0 и 1.1, `trkpt`, `ele`);
- содержит настоящие `time` и `ele` у каждой точки;
- стандарт де-факто для часов, телефонов и организаторов.

TCX — допустимый запасной формат (те же точки и время, но в 2 раза больше
и нужен отдельный парсер). KML — наименее удобен: один `Placemark` на точку,
время в `TimeSpan`, нет трековой семантики, самый большой.

**Что менять в парсере.** Сейчас `GpxTrack` хранит только `lats/lons/eles`,
`time` игнорируется. Нужно добавить:

```dart
final Float64List timesSec;   // epoch seconds, NaN если time нет
bool get hasTime => length > 0 && timesSec.every((t) => !t.isNaN);
```

Память: 200 000 точек × 8 байт = 1.6 МБ — приемлемо. Время нужно и для
калибровки, и для выборки погоды по времени прибытия.

## 5. Погода

### 5.1. Провайдеры и режимы

| Режим | Когда | Источник |
|---|---|---|
| `forecast` | старт ≤ 16 дней | Open-Meteo Forecast |
| `normals` | старт > 16 дней | Open-Meteo Climate / архив за 10 лет |
| `historical` | старт в прошлом | Open-Meteo Archive |

- Основной — Open-Meteo: бесплатно для некоммерческого использования,
  глобально, есть влажность, `apparent_temperature`, осадки, снег, влажность
  почвы, высота нуля изотермы, мультикоординаты и `elevation=`.
- MET Norway (yr.no) — только запасной прогноз (9 дней, нужен свой
  `User-Agent`, нет истории/климата/почвы).
- Всё через `WeatherProvider`, чтобы позже подставить прокси/кэш без
  изменения расчёта.

### 5.2. Переменные

Запрашиваем почасово:

```
temperature_2m, apparent_temperature, relative_humidity_2m,
precipitation, rain, snowfall, wind_speed_10m, snow_depth,
soil_moisture_0_to_7cm, soil_moisture_7_to_28cm,
et0_fao_evapotranspiration, freezing_level_height
```

- **Жара** считается по `apparent_temperature` — в неё уже входят влажность,
  ветер и радиация. Отдельный множитель за влажность не вводим, чтобы не
  удвоить эффект. В интерфейсе показываем **обе** температуры: фактическую и
  «ощущается как». Коэффициенты — стандартные, калибруются только по
  фактическим замерам; главное — влажность уже учтена.
- **Влажность почвы** — оба слоя, `0_to_7cm` и `7_to_28cm`; **дождь**
  (`rain`, мм) и **испарение** (`et0_fao_evapotranspiration`, мм) — поправки
  к ней (§5.4).
- **Снегопад** (`snowfall`, см) нужен отдельно от `precipitation` (мм воды):
  свежий рыхлый снег сопротивляется сильнее, чем лежалый.
- Плотность снега можно грубо оценить как `100 × SWE_мм / depth_см`
  (кг/м³): свежий снег ~50–100, мокрый/укатанный ~300–500.
- `freezing_level_height` может быть `null` (проверено зимой) — обрабатываем
  как «неизвестно», не падаем.
- `elevation=` передаём из GPX: Open-Meteo делает поправку на высоту
  (~0.65 °C / 100 м). Эффект небольшой, но бесплатный.

### 5.3. Время суток и итерации

Погода зависит от времени, а время прибытия — от погоды. Поэтому:

1. Считаем план без поправок.
2. Для каждой точки выборки берём погоду на **плановое время прибытия**.
3. Пересчитываем факторы и план.
4. Повторяем 2–3 раза (обычно хватает 2; останавливаемся, когда изменение
   плана < 1%).

Старт задаёт пользователь (дата/время, локальное). Внутри храним UTC,
показываем локальное. Часовой пояс — из координат (`timezone=auto`) или
фиксируем UTC+3 для РФ; решение: хранить UTC, для отображения брать пояс
устройства.

### 5.4. Влажность почвы

Влажность — главный предиктор грязи. Осадки сами по себе слабый признак:
проверено, что 27.07.2025 за 3 дня выпало 4.4 мм, но почва была сухой
(0.24), а 26.07.2026 — 7 мм за 3 дня и 0.41–0.44. Поэтому основа — влажность
почвы, а дождь и испарение — только поправка.

Запрашиваем почасово (архив это отдаёт, проверено):

```
soil_moisture_0_to_7cm      // верхний слой, реагирует быстро
soil_moisture_7_to_28cm     // глубокий слой, подтверждает устойчивое промокание
rain                        // жидкие осадки, мм
et0_fao_evapotranspiration  // испарение/транспирация, мм
snowfall, snow_depth        // для таяния
```

Считаем эффективную влажность `smEff` (в тех же единицах m³/m³):

```
smBase  = 0.65 × smTop + 0.35 × smDeep

rain12  = Σ rain за 12 ч до старта
et012   = Σ ET0  за 12 ч до старта
rainCorr = 0.04 × clamp((rain12 − 0.6 × et012) / 5, −1, +1)

net72   = Σ rain за 72 ч − 0.6 × Σ ET0 за 72 ч
trendCorr = 0.02 × clamp(net72 / 20, −1, +1)

meltTerm = 0.04 × clamp(meltwater72 / 10, 0, 1)

smEff = clamp(smBase + rainCorr + trendCorr + meltTerm, 0, 0.55)
```

| Компонент | Вес / вклад | Зачем |
|---|---:|---|
| `soil_moisture_0_to_7cm` | **0.65** | с этим слоем взаимодействует обувь |
| `soil_moisture_7_to_28cm` | **0.35** | буфер: если глубоко сухо, верхняя влага быстро уходит |
| дождь/ET0 за 12 ч | ±0.04 | плёнка и лужи, которые модель почвы ещё не усвоила |
| баланс за 72 ч | ±0.02 | тренд: сохнет или продолжает напитываться |
| талая вода | +0.04 | снег тает при положительной температуре |

Почему именно так:

- **0.65 / 0.35.** Верхний слой определяет, что под ногой, но он же
  высыхает за день. Глубокий слой не даёт объявить насыщенный грунт сухим
  после одного солнечного дня.
- **Поправки малы и ограничены.** Влажность почвы уже включает дождь и
  испарение; большие веса были бы двойным счётом. Поэтому дождь и ET0
  двигают `smEff` не больше чем на ±0.06 в сумме.
- **`−0.6 × ET0`.** Не вся испарённая вода уходит из корнеобитаемого слоя;
  коэффициент 0.6 — стартовый, калибруется.
- **Талая вода.** Если `T > 0` и `snow_depth` падает, добавляем воду от
  таяния. Это единственный случай, когда снег увеличивает грязь.

Пороги (калибруются, но 0.40 подтверждён кейсом 26.07.2026):

| `smEff` | Состояние | `wetFactor` |
|---|---|---:|
| < 0.25 | сухо | 1.00 |
| 0.25–0.32 | влажно | 1.04 |
| 0.32–0.40 | мокро | 1.10 |
| > 0.40 | насыщено | 1.20 |
| болото (OSM) | `bog` | 1.35 |

Проверка на реальных днях Суздаля:

| Дата | `smTop` / `smDeep` | `smBase` | Поправки | `smEff` | Состояние |
|---|---:|---:|---:|---:|---|
| 27.07.2025 | 0.24 / ~0.25 | 0.244 | ≈0 | **0.24** | сухо |
| 24.07.2026 | 0.354 / 0.328 | 0.345 | +0.016 | **0.37** | мокро, без грязи |
| 26.07.2026 | 0.430 / 0.384 | 0.414 | +0.031 | **0.45** | насыщено → грязь |
| 28.07.2026 | 0.365 / 0.381 | 0.371 | +0.021 | **0.39** | мокро, без грязи |

То есть 24-е и 28-е остаются ниже порога 0.40, а 26-е уверенно выше —
ровно как вы наблюдали: в двух днях рядом почва была заметно суше, и грязь
практически не мешала.

Если влажность почвы недоступна (старые архивы, сбой), fallback только по
осадкам за 72 ч: `< 2 мм` — сухо, `2–10` — влажно, `10–25` — мокро,
`> 25` — насыщено. Уверенность в таком состоянии низкая, в интерфейсе —
пометка «нет данных о почве».

Зимой влажность не управляет грязью: при отрицательной температуре грунт
мёрзлый, и работают снеговые правила §5.5. `smEff` в этом случае нужен
только для оценки таяния.

### 5.5. Снег: пороги, состояния и глубокий снег

Снег — не «глубина × коэффициент». Сопротивление зависит от плотности, а
плотность — от температуры и свежести. Холодный рыхлый снег проваливается,
околонулевой спекается и держит.

Порог «снег есть» — **2 см** (`snow_threshold = 0.02 м`). Ниже порога
используем обычное покрытие OSM: снег не сплошной.

Состояния и множители:

| `effectiveSnow` | Условие | Состояние | Множитель |
|---|---|---|---:|
| < 0.02 м | любое | покрытие OSM | 1.00 |
| 0.02–0.10 м | `T ≤ 0`, город/посёлок | `packed` | 1.05–1.15 |
| 0.02–0.10 м | `T ≤ 0`, вне населённых пунктов | `loose` | по формуле ниже |
| 0.10–0.30 м | `T ≤ 0` | `loose` | по формуле, до ~1.45 |
| > 0.30 м | `T ≤ 0` | `loose`/`deep` | по формуле, cap 1.90 |
| около 0 °C | город, следы таяния/замерзания | `ice` | 1.15–1.30 |
| `T > +1 °C` | снег ещё лежит | `slush` | 1.15–1.25 |

Формула для рыхлого/лежалого снега:

```
snowFactor = 1 + depthCoeff × min(effectiveSnowM, maxDepthM) × tempCoeff(T)
            + min(freshAddMax, freshSnowCm × freshAddPerCm)
```

```
depthCoeff = 0.21, maxDepthM = 1.00
tempCoeff: −15 °C → 2.60, −12 → 2.40, −8 → 2.00, −5 → 1.73,
           −2 → 1.15, 0 → 0.50, +2 → 0.50
freshAddPerCm = 0.025, freshAddMax = 0.25
```

Ограничение глубины в 1 м нужно, чтобы метровый и двухметровый снег не
различались в разы: после определённой глубины вы уже не проваливаетесь
глубже, а просто идёте медленно. Итог всё равно зажимается глобальным
`clamp` 0.70…2.00.

**Глубокий снег.** При глубине > 0.30 м формула продолжает расти, но
медленнее из-за `maxDepthM`. На практике это означает: 30 см холодного
снега — тяжело, 50 см — тяжелее, но не вдвое. Для очень глубокого снега
(> 1 м) множитель упирается в 1.90, а не уходит в бесконечность.

**`freezing_level_height = null`.** Зимой поле часто пустое. Тогда
оцениваем высоту нуля изотермы сами:

```
FL_est = elevationM + max(0, T) / 0.0065
```

- `T ≤ 0` → снег на поверхности, FL не нужен;
- `T > 0` и `elevationM ≥ FL_est` → снег;
- иначе → дождь/слякоть.

FL используется только для разделения «дождь или снег», а не как
самостоятельный множитель. Основные признаки всё равно `snow_depth`,
`snowfall` и температура.

**Снег при положительной температуре.** Это отдельное правило, потому что
формула для холодного снега здесь даёт неверный знак:

| Условие | Трактовка | Множитель |
|---|---|---:|
| `T > 0`, глубина < 0.02 м | покрытие OSM | 1.00 |
| `T > 0`, 0.02–0.10 м | простая грунтовка / мокрый грунт | 1.10–1.15 |
| `T > 0`, 0.02–0.10 м, грунт насыщен | грунтовка + небольшая грязь | 1.15–1.20 |
| `T > 0`, ≥ 0.10 м | слякоть | 1.15–1.25 |

Смысл: при плюсовой температуре снег укатывается и тает, превращаясь в
мокрую грунтовку. Если слой незначительный — это почти обычный грунт,
максимум чуть грязнее. Только глубокий мокрый снег даёт слякоть.

### 5.6. Снег в населённых пунктах

Снег на трассе зависит не только от погоды, но и от того, где проходит
трек. В городе снег частично расчищен: на дорогах — асфальт, на тротуарах —
укатанный снег или лёд, рыхлый снег остаётся во дворах и парках. В сёлах
чистят меньше, за городом снег не тронут.

Данные:

- `landuse=residential/commercial/industrial/retail` — застроенная
  территория;
- `place=city/town/village/hamlet` — тип населённого пункта;
- `boundary=administrative` + `admin_level=8` — граница города/округа;
- `highway` и `surface` — дорога или тропа и её покрытие.

Классификация точки трека даёт не «город/не город», а **степень
урбанизации** `urbanity` от 0 до 1. Так нет жёсткой границы: окраина,
пригород и село получают промежуточные значения.

| Признак | `urbanity` |
|---|---:|
| внутри `landuse=residential/commercial/industrial/retail` | 1.00 |
| внутри границы `place=city` / `admin_level=8` города | 0.75–1.00 |
| внутри `place=town` | 0.60–0.75 |
| внутри `place=village/hamlet` или в радиусе 0.5–1 км | 0.30–0.45 |
| вне населённых пунктов | 0.00 |

Если несколько признаков пересекаются — берём максимум.

Коэффициент расчистки:

```
clearance = 1 − urbanity × 0.75     // clamp: 0.25 … 1.00
```

| `urbanity` | `clearance` |
|---:|---:|
| 1.00 (город) | 0.25 |
| 0.73 (посёлок) | 0.45 |
| 0.40 (село) | 0.70 |
| 0.00 (поле) | 1.00 |

`clearance` **никогда не равен нулю**: даже в центре города снег полностью
не исчезает — остаются дворы, парки, тротуары. Минимум 0.25.

Поправка на дорогу:

| Дорога | `roadClearance` |
|---|---:|
| магистраль, `primary/secondary/tertiary` | 0.45 |
| местная, `residential/service` | 0.65 |
| тротуар, `footway` | 0.80 |
| грунтовка/тропа, `track/path` | 1.00 |

Эффективная глубина:

```
effectiveSnow = snowDepth × clearance(context) × roadClearance(highway, surface)
```

Дальше — не один множитель, а распределение состояний:

| Состояние | Когда | Множитель |
|---|---|---:|
| `asphalt` | эффективная глубина < 2 см | 1.00 |
| `packed` | 2–10 см, город/посёлок | 1.05–1.15 |
| `ice` | около 0 °C, город, следы таяния/замерзания | 1.15–1.30 |
| `loose` | > 10 см или вне населённых пунктов | по формуле §8.3 |
| `slush` | > +1 °C и снег ещё лежит | 1.15–1.30 |

Если данных OSM нет — `urbanity = 0`, `clearance = 1.0`, полный снег
(консервативно), а не ноль.

Измерение: граница Переславля-Залесского покрывает **20.3%** 40-километрового
зимнего трека по расстоянию (2023, 2024 и 2025 — одинаково). С учётом сёл и
пригородов это как раз около трети, как вы и оценили. Значит, для этого
маршрута снеговой множитель должен применяться не ко всей длине, а к
~70–80%.

Важно: граница города — не то же самое, что расчистка. Внутри города
чистят магистрали, но не парки; поэтому состояние считается по комбинации
«контекст + дорога + температура», а не по одной границе.

Данные OSM по границам и `landuse` кэшируются на трек. Если Overpass
недоступен — fallback на Nominatim reverse (1 запрос/с) или `urbanity = 0`.

Nominatim — это не отдельный источник данных, а геокодер по OSM: он
возвращает тот же полигон границы или точку `place`. Поэтому выбор не
«OSM или Nominatim», а «админграница vs `landuse` vs радиус `place`-точки».
Nominatim удобен, чтобы быстро получить полигон, но истина — в OSM.

Точность здесь намеренно грубая: снег чистят динамически и по мере
возможностей, достоверно предсказать это нельзя. Любое разумное приближение
достаточно; задача модели — не завысить план, а не угадать каждую улицу.

### 5.7. Укатанный снег

Укатанность — **переключатель** в диалоге погоды, по умолчанию **выключен**.
Пользователь включает его, если знает, что трассу укатали организаторы,
снегоходы или её натоптали бегуны. Автоматически по OSM (`piste:grooming`)
он не включается — только может быть предложен как подсказка.

Включённый переключатель делает две вещи:

```
effectiveSnow = effectiveSnow × 0.65          // уплотнение
p(packed) += 0.30, p(loose) −= 0.30           // сдвиг распределения
packedFactor = 1.05 … 1.15
snowFactor   = min(snowFactor, 1.25)          // потолок для укатанного
```

- **Уплотнение.** Укатанный снег в 1.5–2 раза плотнее рыхлого, поэтому
  эффективная глубина умножается на 0.65.
- **Сдвиг состояния.** Часть `loose` переходит в `packed`: по укатанной
  трассе бежится заметно легче.
- **Даже если снег не слеживается.** При плюсовой температуре или свежем
  глубоком снеге укатка невозможна, но впереди идущие всё равно
  пробивают/утрамбовывают колею. Поэтому в этом случае действует
  ограничение `effectiveSnow ≤ 0.70 × snowDepth`, а множитель не
  превышает 1.25. То есть улучшение меньше, чем при настоящей укатке, но
  оно есть.

Переключатель глобальный на трек. Позже можно добавить ручную поправку на
отдельные участки, но для MVP достаточно одного флага.

## 6. Покрытие

### 6.1. Источник — OSM / Overpass

Запрашиваем `way` с `highway` в bbox трека (`out tags geom`), затем для
каждой точки трека ищем ближайший путь в радиусе ~40 м и берём
`surface`, `tracktype`, `ford`.

Теги, которые понимаем:

```
surface = asphalt | concrete | paving_stones | compacted | dirt | ground |
          grass | sand | mud | wood | unpaved | ...
highway = path | track | footway | service | ...
ford    = yes | stepping_stones | ...
```

`unpaved` без уточнения → `dirt`. `surface` отсутствует → `unknown` →
`dirt`. `tracktype` можно использовать как уточнение (grade1…grade5).

### 6.2. Реальное покрытие OSM (замер по трекам)

Треки, ~30 м между сэмплами, путь в радиусе 40 м:

| Трек | Точек-сэмплов | Путь найден | Путь без `surface` | Явный `surface` |
|---|---:|---:|---:|---:|
| 20250727 (45.7 км) | 1473 | 70.4% | 29.4% | 41.0% |
| 20260726 (37.5 км) | 1215 | 73.2% | 23.9% | 49.3% |
| 20251221 (40.2 км) | 1303 | 72.1% | 46.5% | 25.6% |

Распределение явных тегов:

- 20250727: асфальт 21.6%, `ground` 10.3%, трава 5.3%, плитка 1.8%,
  `compacted` 1.7%, дерево 0.2%, брусчатка 0.1%.
- 20260726: асфальт 25.5%, `ground` 12.3%, трава 6.6%, плитка 2.3%,
  `compacted` 2.1%, дерево 0.3%, брусчатка 0.2%.
- 20251221: асфальт 8.3%, `unpaved` 5.8%, `ground` 4.6%, песок 2.4%,
  трава 2.0%, `compacted` 1.6%, дерево 0.5%, `dirt` 0.4%.

Вывод: **явное покрытие есть только у 26–41% длины**, ещё ~28–30% трека
вообще вне путей OSM. Поэтому:

- неизвестное → `dirt` (решение принято);
- в интерфейсе показываем **процент покрытия** и предупреждение, чтобы
  пользователь понимал уверенность;
- калибровка покрытия будет с широкими интервалами — это нормально.

### 6.3. Броды

- `ford=yes` или `highway=ford` → **подтверждённый** брод, сплошная синяя
  линия.
- Пересечение с `waterway` без `bridge`/`tunnel` и без `ford` →
  **возможный** брод, пунктир.
- Позже — подтверждение пользователем на карте (тап).

### 6.4. Мокрость участка

Мокрость считается не по каждому тегу, а по погодному сэмплу,
привязанному к участку: `wetness` = функция `smEff` (§5.4) и типа покрытия
(асфальт сохнет быстрее грунта, болото всегда `bog`).

Правило перехода в грязь: если `wetness = saturated` и тип покрытия —
`dirt`, `ground`, `grass` или `compacted`, участок считается `mud`
(множитель выше, чем у мокрого грунта). Зимой при отрицательной
температуре это правило не применяется — грунт мёрзлый, работают снеговые
правила.

### 6.5. Болото: как определяем

Болото — не просто «мокрый грунт». Это отдельное состояние с собственным
множителем, потому что по нему можно идти по колено, а можно — по настилу.
Определяем по OSM, а при отсутствии данных — по растровым источникам, но
**болото не выдумываем**: если признаков нет, множитель 1.00.

Теги OSM:

| Тег | Что это | `bogFactor` |
|---|---|---:|
| `natural=wetland` + `wetland=bog` | верховое болото, открытое | 1.35 |
| `natural=wetland` + `wetland=fen` | низинное, травяное | 1.25 |
| `natural=wetland` + `wetland=marsh` | заболоченный лес/топь | 1.30 |
| `natural=wetland` + `wetland=swamp` | топь, вода и деревья | 1.30 |
| `natural=wetland` + `wetland=reedbed` | тростник | 1.20 |
| `natural=wetland` + `wetland=wet_meadow` | мокрый луг | 1.15 |
| `natural=bog` (устаревший) | болото | 1.35 |
| `natural=marsh` / `natural=swamp` | топь | 1.30 |
| `surface=peat` | торфяная поверхность | 1.30 |
| `landuse=peat_extraction` | торфоразработки | 1.40, лучше обходить |
| `highway=path` внутри wetland без `surface` | тропа по болоту | 1.25 |
| `highway=boardwalk` / `surface=wood` внутри wetland | настил | 1.05 |
| `seasonal=yes` + wetland | сезонно заболоченное | фактор только во влажный сезон |

Алгоритм:

1. В bbox трека запрашиваем полигоны `natural=wetland|bog|marsh|swamp`,
   линии `surface=peat`, `landuse=peat_extraction` и ближайшие `highway`.
2. Для каждой точки трека — point-in-polygon с буфером ~10 м. Если точка
   внутри полигона, это кандидат в болото.
3. Если ближайшая дорога — `highway=boardwalk` или `surface=wood`, ставим
   `boardwalk` 1.05: по настилу бежится почти как по грунту.
4. Если OSM пуст — смотрим растровые источники (см. ниже). Они дают только
   «возможно болото» с низкой уверенностью.
5. Если нет ни одного признака — болота нет, множитель 1.00.

Растровые fallback-источники:

| Источник | Признак | Уверенность |
|---|---|---:|
| ESA WorldCover 10 м | класс 90 (herbaceous wetland), 95 (mangroves) | 0.5 |
| Copernicus Land Cover 100 м | класс wetland | 0.4 |
| SoilGrids | доля торфа / органического углерода высокая | 0.4 |
| DEM | плоский участок, низкий дренаж, локальное понижение | 0.2 |

DEM и SoilGrids сами по себе болото не назначают — только повышают
уверенность, если рядом есть wetland или торф. Иначе любой сырой луг в
низине стал бы болотом.

Зимой болото **не промерзает насквозь**. Снег работает как одеяло: под ним
грунт остаётся жидким, и мороз до него не добирается. Замерзает только
верхняя корка, и только если снега нет и около недели держится −10 °C и
ниже. Поэтому:

| Условие | Состояние | `bogFactor` |
|---|---|---:|
| снег ≥ 5 см | под снегом жижа, не мёрзнет | по таблице, без снижения |
| снега < 5 см и `T5 ≤ −10 °C` ≥ 7 дней | мёрзлая корка сверху | 1.20 |
| иначе | обычное болото | по таблице |

`T5` — средняя температура воздуха за 5 дней. Даже мёрзлая корка не делает
болото быстрым: она может проломиться, а под ней — жижа. Поэтому снижение
только до 1.20, а не до 1.05. Если лежит снег, `groomed` тоже не помогает:
укатывается снег, а не болото под ним — `bogFactor` остаётся полным.

На графике болото рисуется широкой полосой (см. §11.2). Интенсивность
цвета — по `bogFactor`, чтобы открытое болото отличалось от мокрого луга.

### 6.6. Уточнение неизвестного покрытия

Явный `surface` есть только у 26–49% длины трека. Остальное нельзя
оставлять «просто грунтом», если есть другие данные. Используем **все
доступные источники** и голосуем взвешенно, а не берём первый попавшийся.

| Приоритет | Источник | Вес | Что даёт |
|---:|---|---:|---|
| 1 | OSM `surface` | 1.00 | точный тип покрытия |
| 2 | OSM `tracktype` (`grade1…5`) | 0.80 | `compacted` … `dirt` |
| 3 | OSM `highway` | 0.60 | `footway`/`path`/`track`/`service` |
| 4 | OSM `natural`, `landuse`, `wetland`, `seasonal` | 0.50 | лес, луг, пашня, болото |
| 5 | ESA WorldCover 10 м | 0.40 | класс поверхности |
| 6 | Copernicus Land Cover 100 м | 0.30 | класс поверхности |
| 7 | MODIS 500 м | 0.20 | грубый класс |
| 8 | SoilGrids | 0.20 | текстура/дренаж, риск грязи |
| 9 | по умолчанию | — | `dirt` |

Правила:

- Явный `surface` с весом 1.00 **не перекрывается** растром: асфальт
  остаётся асфальтом, даже если WorldCover назвал клетку «застройкой».
- Если явного тега нет, итоговый фактор — взвешенное среднее по доступным
  источникам, а не жёсткий выбор. Например, `highway=path` + WorldCover
  «лиственный лес» → лесная подстилка (`ground`), а не асфальт.
- `unknown` остаётся только когда нет вообще ничего; тогда `dirt`.
- В интерфейсе показываем, сколько длины покрыто явными тегами и сколько
  добавлено растрами. Это честнее, чем одна цифра «73%».

Реализация на 12.11.2026 — **приоритетный выбор**, а не числовое
взвешивание (веса сохранены как `confidence` источника и показываются в
`SurfaceRun.confidence`):

1. явный `surface` → `tracktype` → жёсткая дорога по `highway`;
2. для «мягкой» тропы растр уточняет покрытие только мягкими классами
   (`dirt`, `ground`, `grass`, `sand`) — тропа не становится асфальтом;
3. если дороги OSM нет вообще, растр заполняет пробел любым классом,
   включая застройку (`pavingStones`);
4. вода (`WorldCover` 80) не даёт кандидата: ни покрытия, ни брода;
5. `wetland`/`mangrove` дают болото с уверенностью 0.5; OSM-болото имеет
   уверенность 1.0 и всегда важнее растрового.

Соответствие классам ESA WorldCover:

| Класс | Покрытие |
|---|---|
| 10 дерево | `ground` (лесная подстилка) |
| 20 кустарник | `ground` |
| 30 трава | `grass` |
| 40 пашня | `dirt` |
| 50 застройка | `pavingStones` |
| 60 голая земля | `ground` |
| 70 снег/лёд | `ground` |
| 80 вода | нет кандидата: вода не назначает ни покрытие, ни брод |
| 90 водно-болотные травы | `grass` + болото, уверенность 0.5 |
| 95 мангры | `ground` + болото, уверенность 0.5 |
| 100 мох/лишайник | `ground` |

Важно: «застройка» не превращает лесную тропу в асфальт. Сначала смотрим
`highway` и `surface`, растр — только для пробелов. Поэтому вес OSM-тегов
всегда выше растровых.

Данные: ESA WorldCover 2021 v200, лицензия **CC BY 4.0**
(`https://esa-worldcover.org`). Тайлы читаются из COG на
`esa-worldcover.s3.eu-central-1.amazonaws.com` через HTTP Range; полный
тайл 3°×3° (~67 МБ) не скачивается.

### 6.7. Почему не берём данные с картинки карты

Идея «посмотреть на отрисованную карту» технически возможна, но как
источник данных не подходит:

- тайлы — это картинка, а не данные: цвет кодирует дороги, дома, подписи,
  рельеф, значки; отделить грунтовку от лесной тропы по цвету ненадёжно;
- стиль зависит от слоя: OSM, CyclOSM и OpenTopoMap рисуют одни и те же
  теги по-разному, модель пришлось бы обучать на каждый стиль;
- правила тайловых серверов запрещают массовую загрузку и извлечение данных;
  анализировать тайлы на масштабе нельзя без разрешения;
- подписи, антиалиасинг и генерализация по зуму добавляют шум;
- карта неплохо показывает ландшафт (лес, поле), но не различает
  асфальт / `compacted` / `dirt` и вообще не показывает грязь.

Что использовать вместо:

- **векторные теги OSM** — уже используем; добавить `natural`, `landuse`,
  `wetland`, `seasonal`, чтобы уточнять `unknown`: лес → лесная подстилка,
  `natural=wetland` → болото, `landuse=meadow` → трава;
- **готовые растровые продукты классификации** (ESA WorldCover 10 м,
  Copernicus Land Cover, MODIS) — это не картинки, а классы поверхности
  (деревья, кустарник, трава, пашня, застройка, вода, болото). Бесплатны,
  закрывают пробелы OSM;
- **почвенные и рельефные данные** (SoilGrids, Copernicus DEM) — текстура,
  дренаж, уклон; помогают оценить риск грязи;
- **ручное подтверждение** — тап по участку на карте. Надёжнее
  компьютерного зрения и создаёт локальную поправку.

Итог: карта — для отображения; данные — из OSM-вектора и растровых
классификаторов. Для грязи лучший предиктор — влажность почвы + осадки +
`landuse`/`wetland`, а не цвет пикселей.

| Покрытие \ Кроссовки | Road | Trail | Minimal |
|---|---:|---:|---:|

| мокрый асфальт | 1.08 | 1.03 | 1.05 |
| сухой грунт | 1.06 | **1.00** | 1.02 |
| мокрый грунт | 1.15 | 1.04 | 1.08 |
| насыщенный грунт / грязь | **1.35** | 1.10 | 1.20 |
| трава | 1.05 | **1.00** | 1.01 |
| песок | 1.15 | 1.04 | 1.08 |
| укатанный снег | 1.25 | 1.05 | 1.15 |
| глубокий снег | 1.60 | 1.20 | 1.40 |
| брод / мокрые ноги | 1.10 | 1.02 | 1.05 |

Кейс 26.07.2026: по ощущениям бежать в дорожных кроссовках было почти

**1.35** (решение принято; дальше можно уточнять в пределах 1.35–1.50).

Если кроссовки не выбраны — множитель 1.00 (только покрытие и погода).

## 8. Формулы и профиль

### 8.1. Множители

На каждом участке:

```
surfaceFactor = typeFactor(surface)
              × wetFactor(wetness)
              × shoeFactor(shoe, surface, wetness)

weatherFactor = heatFactor(apparentC)
              × snowFactor(snowDepth, airTempC, freshSnowCm,
                           elevationM, freezingLevelM)

segmentTime = lengthKm × flatPaceSecPerKm × gapFactor
            × surfaceFactor × weatherFactor
```

`snowFactor` намеренно зависит от температуры: при околонулевой температуре
снег плотный и катится лучше, при сильном морозе — рыхлый и проваливается.
Глубина без температуры даёт неверный знак (см. §10.3.2).

`gapFactor` — уже существующий Minetti. Итог — сумма по участкам; стоянки
прибавляются отдельно, как сейчас.

### 8.2. Ограничения

- Каждый множитель и итог зажимаются в `[min, max]` (стартово `0.70…2.00`),
  чтобы один сбойный сэмпл не сломал план.
- Если для участка нет данных — множитель 1.00 и пометка «нет данных», без
  экстраполяции.

### 8.3. Один глобальный профиль

Его же использует калибровка. Формат:

Влажность почвы и болото:

```
smBase = weightTop × smTop + weightDeep × smDeep

               + rain12Coeff × clamp((rain12 − 0.6 × et012) / 5, −1, +1)
               + trend72Coeff × clamp(net72 / 20, −1, +1)
               + meltCoeff × clamp(meltwater72 / 10, 0, 1), 0, 0.55)

wetness = dry | damp | wet | saturated   // по dryBelow/dampBelow/wetBelow

```

Пороги `dryBelow = 0.25`, `dampBelow = 0.32`, `wetBelow = 0.40` — стартовые;
0.40 подтверждён кейсом 26.07.2026. Если `wetness = saturated` и покрытие
`dirt/ground/grass/compacted`, участок становится `mud`.

Снеговой множитель:

```
effectiveSnow = snowDepth × clearance(settlement)
              × roadClearance(highway, surface)
              × (groomed ? 0.65 : 1.00)

snowFactor = 1 + depthCoeff × min(effectiveSnowM, maxDepthM) × tempCoeff(T)
            + min(freshAddMax, freshSnowCm × freshAddPerCm)

// при T > 0:
//   effectiveSnow < 0.02 → покрытие OSM
//   0.02…0.10 → dirtFactor 1.10…1.15 (mudFactor, если грунт насыщен)
//   ≥ 0.10    → slushFactor 1.15…1.25

// при groomed:
//   snowFactor = min(snowFactor, factorCap)
//   effectiveSnow = min(effectiveSnow, maxDepthScale × snowDepth)
```

Если известны вероятности состояний, итог считается как
`snowFactor = Σ p(state) × factor(state)`, где `asphalt` = 1.00,
`packed` / `ice` / `slush` — из `snowState`, `loose` — по формуле выше.
Для `groomed` распределение сдвигается: `p(packed) += packedShift`,
`p(loose) −= packedShift`.

`tempCoeff` уменьшается к 0 °C: тёплый плотный снег почти не тормозит,
холодный рыхлый — тормозит сильно. Коэффициенты подобраны по зимам 2023/2024
(§10.3.2) и требуют проверки на других трассах. `maxDepthM = 1.00` не даёт
очень глубокому снегу уйти в бесконечность, `deepCap = 1.90` — потолок.

Чтобы не удвоить эффект: сезонный снег учитывается **только** через
`snowFactor`, а тип покрытия остаётся базовым (асфальт/грунт/трава).
`snow_packed` и `snow_deep` в профиле покрытия — только для постоянного
снега/льда (ледник, OSM `natural=glacier`) или ручного выбора; тогда
`snowFactor` для этого участка = 1.00.

## 9. Отбор точек погоды

### 9.1. Базовый шаг

20 км по дистанции. Меньше — бессмысленно для глобальной модели, больше —
теряем высоту и время суток.

### 9.2. Дополнительные точки

- середины однородных участков покрытия и высоты;
- вершины и днища ущелий (локальные экстремумы высоты);
- участки покрытия длиннее 2 км — по границам;
- броды.

### 9.3. Лимит

Не больше **50 точек на 100 км**. Для 100-километровой дистанции это
20 базовых + до 30 дополнительных.

### 9.4. Важно: сетка модели грубее шага

Проверено на реальном треке: Open-Meteo Archive **привязывает координаты к
сетке ~5–8 км**. Пять запрошенных точек летнего трека дали всего **две
уникальные ячейки** (четыре точки схлопнулись в одну). Зимой — три ячейки
на пять точек.

Следствия:

- 20 км — уже достаточно мелко для исторической погоды; более частые точки
  не добавят информации, кроме поправки на высоту;
- перед запросом **дедуплицируем точки по округлению ~0.05°**, чтобы не
  тратить квоту;
- для прогноза сетка может быть мельче (1–2 км), поэтому дедупликацию
  делаем по ответу (`latitude/longitude` в ответе), а не только по запросу.

## 10. Калибровка на реальных треках

### 10.1. Что нужно

1. Разобрать GPX с `time` и `ele`.
2. Пересчитать фактические скорости по участкам (исключая стоянки: разрыв
   > 60 с или скорость < 0.7 м/с).
3. Посчитать GAP-фактор по высоте.
4. Привязать к каждому участку покрытие, мокрость и погоду на время
   прохождения.
5. Оценить коэффициенты так, чтобы `predicted ≈ actual`.

Модель: `log(v_flat_actual) = log(v_flat_base) + Σ β_k x_k`, решение —
регуляризованный МНК (ridge), с ограничениями на знак и диапазон. Мало
данных по классу → fallback на стартовое значение + низкая уверенность.

### 10.2. Неполные треки (DNF)

Трек может закончиться раньше финиша таблицы. Правила:

- считаем только покрытый диапазон `[0, X]`;
- строки таблицы за `X` — «нет данных», множитель 1.00, без ошибки;
- не экстраполируем и не требуем достижения финиша;
- если точек < 2 или нет времени — фича выключается с сообщением, не падает;
- если трек начинается позже старта таблицы — учитываем `startOffsetM`.

не знает, укатана ли трасса. Поэтому снеговой множитель «мягкий», а
уверенность в нём ниже, чем в дождевом.

### 10.3.3. Снег: пороги, глубокий снег и fallback

**Порог.** 2 см. Ниже — снег не сплошной, работает покрытие OSM. Это
согласуется с 2025-м: в поле 2 см, но на трассе асфальт и слякоть, и
множитель должен быть близок к 1.00, а не к снеговому.

**Состояния.** До 10 см в городе — `packed` (1.05–1.15), вне города —
`loose` по формуле. 10–30 см — `loose`, 30 см–1 м — `loose` с ростом,
> 1 м — потолок 1.90. Около 0 °C в городе — `ice` 1.15–1.30. При `T > +1 °C`
и лежащем снеге — `slush` 1.15–1.25.

**Глубокий снег.** Формула линейна по глубине только до `maxDepthM = 1.00`.
Дальше множитель не растёт: на очень глубоком снегу вы уже не проваливаетесь
пропорционально глубине, а просто идёте медленно. Потолок 1.90. Это
защищает от абсурдных значений на метровом и двухметровом снеге.

**`freezing_level_height = null`.** Зимой поле часто пустое (проверено).
Fallback:

```
FL_est = elevationM + max(0, T) / 0.0065
```

- `T ≤ 0` → снег на поверхности;
- `T > 0` и `elevationM ≥ FL_est` → снег;
- иначе → дождь/слякоть.

FL — только для разделения «дождь/снег». Если и его нет, остаются
`snow_depth`, `snowfall` и температура — их достаточно для множителя.

**Положительная температура.** Отдельное правило: при `T > 0` снег
укатывается и тает. Глубина < 2 см — покрытие OSM; 2–10 см — простая
грунтовка/мокрый грунт (1.10–1.15), при насыщенном грунте — небольшая грязь
(1.15–1.20); ≥ 10 см — слякоть (1.15–1.25). Это соответствует вашему
наблюдению: снег при плюсе — не «глубокий снег», а мокрая грунтовка.

**Укатанный снег.** Переключатель §5.7 уменьшает эффективную глубину в
0.65 раза и сдвигает распределение к `packed`. Если условия не позволяют
слежаться (плюс или свежий глубокий снег), всё равно действует
`effectiveSnow ≤ 0.70 × snowDepth` и потолок 1.25: впереди идущие снижают
глубину от максимума, но улучшение меньше, чем при настоящей укатке.

**Что осталось проверить.** Слякоть при +1…+4 °C и переход через 0 °C
(таяние/замерзание) на других треках; влияние `groomed` на реальный темп;
поведение на постоянном снегу/леднике (`snow_packed`/`snow_deep`).

### 10.4. Проверка API

- Archive API: работает, отдаёт историю по часам.
- Climate API: работает, 10-летние нормы по дням (проверено
  2015-07-25…2024-07-29, 3293 дня, ~92 КБ).
- Archive с `daily` за 10 лет: работает, ~92 КБ — хороший вариант для норм
  без отдельного Climate API.
- Forecast host в тестовом окружении не отвечал (таймаут), archive и
  climate — отвечали. Это сетевая особенность окружения, не дизайн; на
  устройстве прогноз нужно проверить отдельно.
- Overpass: публичные серверы перегружены, помогал
  `overpass.private.coffee`; нужен список зеркал и повтор с backoff.

### 10.5. Кросс-проверка на Suunto

В `userTracks/User1` добавлены пять треков Suunto (2025–2026). Они
использовались только для проверки, а не для переобучения профиля:

| Группа | Треков | GAP-темп |
|---|---:|---:|
| Huawei (Суздаль и окрестности) | 13 | 386–672 с/км |
| Suunto | 5 | 313–403 с/км |

- Погодные даты частично пересекаются, но базовая скорость групп разная:

## 11. Интерфейс

### 11.1. Чекбоксы в меню-шестерёнке

- `Покрытие`, `Погода`, `Кроссовки` — три независимых чекбокса.
- Клик по чекбоксу **открывает диалог** (источник, время старта, кроссовки,
  профиль). Чекбокс остаётся снятым, пока не нажато «Применить».
- В диалоге погоды — переключатель **«Укатанный снег»**, по умолчанию
  выключен. Включённый означает, что трассу укатали/натоптали: эффективная
  глубина снега уменьшается, состояние сдвигается к `packed` (§5.7).
- Если доступны только климатические нормы, а прогноза нет — погодная
  галочка либо не показывается, либо сразу помечена «нет прогноза»;
  погодная полоса на графике **не рисуется**, погодный множитель 1.00.
- «Отмена»/закрытие — состояние не меняется.
- После применения — пересчёт плана и обновление графика.
- Ниже трёх чекбоксов — пункт **«Коэффициенты окружения»**: полноэкранный
  редактор всех коэффициентов профиля с кнопками «Сбросить» и
  «Сохранить». Сохранение пишет `FactorProfileStore`, удаляет кэш текущего
  трека и пересчитывает окружение.
- Кроссовки: `Дорожные (плоские)`, `Трейловые (протектор)`, `Трейловые с
  шипами`. Если модель не выбрана, диалог открывается на трейловых и
  применяет их — множитель не остаётся единицей по умолчанию.
- Строка состояния (`обновлено чч:мм · покрытие · погода`) показывается
  справа от кнопки режима, а не под кнопками таблицы. Для данных прошлых
  суток добавляется дата.

### 11.2. График высот

Без отдельной строки таблицы и без легенды на самом графике.

**Низ графика — покрытие:**

- линия по типу покрытия (цвет на тип);
- вторая синяя линия — мокрость;
- широкая полоса — болото;
- синяя вертикальная линия — брод: сплошная подтверждённый, пунктир
  возможный.

**Верх графика — погода:**

- полупрозрачная полоса по `apparent_temperature` (цветовая шкала);
- без легенды, без больших полей;
- трек и профиль остаются видимыми;
- если прогноза нет (только нормы) — **полосы нет вообще**, а не серая
  заглушка.

Под графиком — расшифровка долей покрытия. После каждой доли в скобках
показывается, сколько времени добавил этот тип покрытия: `Грунт 50% (+25%)`.
Отдельная строка погоды показывает добавленное время и процент:
`Погода: +0:12 (+10%)`. При открытом сегменте и доли, и погода считаются
только по этому сегменту; сегменты листаются свайпом влево/вправо.

### 11.3. Карта (позже)

`flutter_map` + тайлы OSM / CyclOSM / OpenTopoMap. CyclOSM и OpenTopoMap —
это стили отрисовки OSM, а не источники данных о покрытии. Офлайн-тайлы —
позже. Слой покрытия и погоды — полупрозрачный, без больших отступов.

## 12. Лимиты API и масштабирование

Open-Meteo бесплатно (некоммерческое использование):

- 600 запросов/мин, 5 000/час, 10 000/день, 300 000/месяц;
- мультикоординатный запрос считается как несколько вызовов;
- 1 000 пользователей × 50 точек = 50 000 вызовов/день — больше дневного
  лимита.

Поэтому:

- MVP — прямые вызовы;
- `WeatherProvider` уже сейчас проектируем под прокси/кэш;
- кэш по (округлённая координата, дата, час, модель) — резко снижает
  повторы;
- при росте — свой backend с кэшем и одним ключом.

### 14.2. Что осталось

Всё перечисленное — калибровка и проверка на данных. Ни один пункт не
блокирует MVP; калибровка — отдельная сессия после MVP.

1. **Жара.** Коэффициенты `heat` — стартовые; откалибровать на горячих
   гонках. Главное — влажность уже учтена через `apparent_temperature`.
2. **Влажность почвы.** Формула и веса зафиксированы, проверены на пяти
   днях Суздаля (24, 26, 28.07.2026 и 27.07.2025, 13.06.2026). Нужно
   прогнать на большем числе треков и уточнить `0.6 × ET0` и порог 0.40.
3. **Снег.** Проверено на двух зимах. Нужны ещё, особенно слякоть при
   +1…+4 °C, переход через 0 °C и влияние `groomed` на реальный темп.
4. **Болото.** Физика зимней логики зафиксирована: под снегом не мёрзнет,
   корка только при бесснежье и −10 °C неделю. Осталось проверить пороги
   растровых fallback-ов и `frozenTop` на реальных зимних болотах.
5. **Сетка прогноза.** Дедупликация 0.05° достаточна для истории; для
   прогноза сетка мельче — проверить на устройстве.
6. **Прокси/кэш.** Порог, после которого прямые вызовы Open-Meteo нужно
   заменить своим backend.
