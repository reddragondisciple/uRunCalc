Посмотрел проект: Flutter, чистый Dart-слой расчётов (pace_calculations.dart), таблица ПП с distances, planPaces, planTimes и уже готовой логикой пересчёта плана. Для этой фичи архитектура подходит очень хорошо — всё упирается в математику и качество данных, а не в инфраструктуру.
Короткий вердикт
Реализуемо полностью, без бэкенда и без новых тяжёлых зависимостей. Это не «research project», а нормальная инженерная задача на 3–5 итераций. Главные риски — не в коде, а в двух местах: шум высот в GPX и то, что модель темпа всегда будет оценкой, а не предсказанием.
По частям
1. Парсинг GPX — просто.
GPX это XML с trkpt lat lon ele time. Хватает пакета xml (чистый Dart, работает на всех платформах). Нужно аккуратно обработать: несколько trkseg, отсутствие ele, отсутствие time, дубли точек, огромные файлы (100k+ точек — парсить в изолированном Isolate).
2. Расстояние и набор высоты — средне.
Здесь основная «грязь». Высоты с GPS/барометра шумят, и наивное суммирование всех положительных приращений даёт завышенный D+ в 1.5–2 раза. Нужно:
- сглаживание профиля (скользящее среднее или Savitzky–Golay),
- порог гистерезиса при накоплении D+/D− (например, игнорировать колебания < 2–3 м),
- расчёт расстояния по haversine, при желании — 3D-дистанция.
Это стандартная, хорошо известная задача (так работают Strava/ITRA). Результат всё равно будет отличаться от «истины» на ±10–20% — это нормально и должно быть честно показано в UI.
3. Привязка трека к таблице ПП — просто, но это ключевое место.
У вас в таблице уже есть ряд Расстояние — то есть ПП заданы километрами. Значит трек не должен «создавать» чекпойнты: он должен ресемплироваться по накопленной дистанции и отдавать высоту/уклон в точках ПП. Дальше по каждому сегменту считаются D+, D−, средний уклон.
Нюанс: если сумма трека не совпадает с последним ПП (98 км против 102 в таблице) — нужно масштабировать или предупреждать, а не молча обрезать.
4. Модель корректировки темпа — математически просто, но здесь надо быть аккуратным.
Важный технический совет: не считайте темп по среднему уклону сегмента. Сегмент «вверх 5 км, потом вниз 5 км» имеет средний уклон ≈ 0 и даст плоский темп, хотя по времени он тяжелее. Правильно — интегрировать по треку: для каждого участка ds считать уклон i, брать скорректированную скорость и суммировать ds / v(i). Тогда D+/D− остаются только для отображения, а время считается корректно.
По формуле есть два разумных варианта:
- GAP на основе Minetti (2002) — энергозатраты ходьбы/бега от уклона:
Cr(i) = 155.4i⁵ − 30.4i⁴ − 43.3i³ + 46.3i² + 19.5i + 3.6
Коэффициент темпа = Cr(0) / Cr(i). Физически обосновано, легко тестируется, один параметр — опорный «плоский» темп.
- Практическая линейная модель — «+X сек/км на каждый 1% подъёма», с отдельным, более слабым коэффициентом на спуск. Проще объяснить пользователю и проще тюнить.
Рекомендую Minetti с обязательным clamp уклона (примерно ±20–25%): на крутых спусках полином начинает предсказывать нереально быстрый бег. Дополнительно дать пользователю один ползунок «агрессивность/осторожность на спуске» — трейловые бегуны очень по-разному бегут вниз, и это честнее, чем делать вид, что модель универсальна.
5. График высот — просто.
CustomPainter, без библиотек: профиль, маркеры ПП, подсветка выбранного сегмента, курсор с расстоянием/высотой/уклоном. Для 10–20k точек — обязательный даунсемплинг (min/max по пиксельным бакетам или LTTB), иначе будет тормозить на слабых телефонах. Это буквально 30 строк.
6. Хранение — единственное место, где есть архитектурное решение.
SharedPreferences не годится для GPX на несколько мегабайт. Варианты: хранить файл в каталоге приложения (path_provider) и в prefs держать только метаданные, либо хранить в prefs даунсемплированный профиль (500–1000 точек) и статистику по сегментам. Второй вариант проще и достаточно для вашей задачи — сам трек после анализа не нужен.
Как это ложится на текущий код
- lib/features/gpx/ — парсер, ресемплинг, сглаживание, D+/D−, GAP-модель. Всё чистыми функциями, как pace_calculations.dart, → покрывается юнит-тестами без Flutter.
- PaceTableData — добавить опциональные segmentAscent, segmentDescent, profileSource (флаг «план построен по треку»). Это важно: сейчас логика сдвига плана не знает, откуда взялись planPaces, и после ручной правки трековый план не должен «переезжать» неожиданно.
- Заполнение — в planPaces + planTimes, то есть переиспользуется существующий механизм пересчёта и подсветки. Новый виджет таблицы не нужен.
- Строки в таблице — опционально добавить Набор / Сброс по сегментам и Профиль (мини-график), но это уже UI-обсуждение.
- app_strings.dart — сразу с локализацией, как у вас принято.
- Зависимости: xml (pure Dart), file_selector (официальный плагин Flutter для выбора файла), возможно path_provider. Риск для CI минимальный: плагины не вызываются в тестах.
Где будут расхождения с реальностью (и как это подать)
Это стоит проговорить заранее, потому что от этого зависит UX:

Блокирующий вопрос: откуда в GPX чекпойнты
В GPX как формате нет чекпойнтов. Есть wpt (путевые точки), rtept (точки маршрута), trkseg (сегменты трека) и собственно trkpt. Поэтому фраза «если в треке их больше» требует уточнения:
- Вариант A: организаторы кладут ПП как wpt с именами. Тогда всё хорошо, но нужно решить, как сопоставлять: по имени (язык/написание может отличаться), по порядку, или по ближайшему километру. И что делать с «лишними» — это могут быть не ПП, а источники воды, вершины, повороты.
- Вариант B: чекпойнты — это границы trkseg (иногда трек режут по ПП).
- Вариант C: в треке чекпойнтов нет вообще, и «обновить чекпойнты» значит «расставить N точек равномерно по треку». Это полезно, но тогда текущие расстояния ПП теряются.
Мой совет: поддержать A и C, а привязку делать по накопленной дистанции с предпросмотром (таблица «трек → колонка» перед применением), с авто-подбором по имени как подсказкой. Если количество wpt не совпало с числом ПП — показать выбор, какие оставить, а не угадывать молча. Это единственное место, где можно легко испортить данные пользователя.
